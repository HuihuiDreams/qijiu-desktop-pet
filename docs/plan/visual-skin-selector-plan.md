# 桌面宠物可视化皮肤选择窗 (Visual Skin Selector) 规划文档

## 1. 痛点与需求背景 (Problem Statement)
目前项目内置了 3 套皮肤（`default`, `birds`, `animal_ears`），用户通过托盘菜单（Tray Menu）的单选列表进行切换。
随着后续皮肤数量的增加（预计达到 10~30 套甚至更多），纯文字菜单列表会变得冗长且难以直观选择。用户难以仅凭借文字命名判断皮肤的具体外观与风格。
我们需要在**不打断工作、保持轻量级**的前提下，打造一个响应极速、可视化选图的皮肤画廊面板。

## 2. 方案方向与架构决策 (Recommended Direction)
采用 **方向 A：按需即用的“极速选图弹窗” (Spotlight / Gallery 模式)**。

### 核心交互与视觉逻辑
1. **触发方式**：用户点击托盘菜单项 `[选择皮肤...]`（或通过快捷键/桌宠交互按钮呼出）。
2. **呈现形态**：主进程创建一个轻量级、无边框（或简洁居中悬浮）的 `BrowserWindow`。界面采用网格布局展示所有已扫描到的皮肤缩略图（封面图）与展示名称。
3. **视觉风格与状态窗口对齐**：选肤窗口的 Electron 属性配置与前端 UI 风格，必须严格对标现有的修仙状态窗口 (`statusWindow` / `status.html` / `status.css`)。采用无边框透明 (`transparent: true, frame: false, hasShadow: false`)、浮动顶层 (`alwaysOnTop: 'floating'`)；UI 复用 `index.css` 的修仙设计设计语言（半透明磨砂面板 `var(--panel-bg)`、双层边框纹理 `::before` / `::after`，以及青金渐变底边），保证整体视觉沉浸与品质感一致。
4. **即点即走**：用户单击任意皮肤卡片后，窗口立刻发送 `switch-skin` 指令通知桌宠主渲染进程换装，同时选肤窗口立即销毁或自动隐藏。
5. **失焦自动退出**：如果用户点击了窗口外区域（发生 `blur` 事件），选肤窗口立刻自动关退，零心智负担。

## 3. 核心假设验证 (Key Assumptions to Validate)
- [ ] **封面图代表性**：仅展示一帧代表性静态封面（如 `right.webp` 或 `cultivate.webp`），足以让用户直观辨识并做出决策，无需渲染复杂的序列帧。
- [ ] **极速响应与启动时间**：加载 10~30 张本地 WebP 图片的子窗口启动延迟需控制在 100ms 以内。建议测试“按需创建并销毁”与“预加载隐藏并复用”两种策略的内存与耗时表现。
- [ ] **多显示器与高 DPI 适配**：必须基于 `displayBounds.js` 等现有模块，确保弹窗在鼠标所在的当前显示器正确居中弹出，不发生跨屏偏移。

## 4. MVP 范围界定 (MVP Scope)

### What's in (核心包含)
- **主进程支持**：在 `main.js` 中新增对标 `statusWindow` 属性（透明、无边框、浮动顶层）的选肤窗口创建与管理逻辑，复用 `scanAvailableSkins()` 并向前端发送皮肤资产路径。
- **画廊渲染 UI**：使用标准 Vanilla HTML/CSS 构建极简网格画廊，复用现有状态窗口（`status.css`）的视觉风格（修仙风半透明面板、双边框纹理与字体变量）；支持卡片悬停高亮微动效，并明确标识当前正在使用的皮肤。
- **IPC 联动**：点击卡片发送 IPC 请求切换当前皮肤，并触发退窗。
- **失焦隐藏**：监听窗口 `blur` 事件自动退出。

### What's out (后续迭代或暂不包含)
- 搜索框与复杂分类过滤标签（在皮肤数量 < 30 套时优先保证极简）。
- 实时多帧循环播放动效预览。
- 第三方皮肤的在线商城下载、解压与删除管理。

## 5. 不做的权衡 (Not Doing and Why)
- ❌ **不做常驻式“设置/衣橱”大窗口**：违背用户快捷切换、不打断工作的初心；常驻多个独立 OS 窗口会增加管理复杂度并消耗无谓内存。
- ❌ **不做“点击预览 -> 再次确认应用”的两步确认流**：在 10~30 套规模下，两步操作显得拖沓，即见即得（一键切换）体验最佳。
- ❌ **不做同屏多卡片实时动画渲染**：同时渲染几十个 WebP 序列帧极易造成 CPU/GPU 负担骤升，违背修仙桌宠挂机省系统资源的根本准则。

## 6. 待决与开放问题 (Open Questions)
- **窗口管理策略**：为了保证呼出时的丝滑感，建议后续编码前对比测试：
  1. 方案 A：每次触发创建新窗口，关闭后直接 `destroy()`（释放内存彻底，但冷启动约有几十毫秒）。
  2. 方案 B：应用启动时初始化并 `hide()`，呼出时 `show()`，更新列表时局部刷新（弹出最快，但常驻一个隐藏页面内存）。
