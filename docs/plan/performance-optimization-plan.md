# 性能优化计划

## 背景与目标

2026-07-23 的初步空闲采样显示，主渲染循环保持约 60 FPS，10 秒内没有超过
20ms 的帧或 Long Task；因此不应在缺少证据时重构游戏循环或精灵预加载。
当前需要优先验证三类候选风险，而不是预先认定它们是瓶颈：

1. 覆盖整个虚拟桌面的透明窗口是否显著增加基础私有内存。
2. 强天气特效是否在真实 GPU 环境中造成脚本、渲染或合成压力。
3. 主窗口加载前清除 Chromium 缓存是否造成用户可感知的启动等待。

本计划以“先测量、后定位、再优化、最后复测”为原则。每次只处理一个原子
任务；凡修改生产代码，都必须在同一步更新对应测试、`CHANGELOG.md` 和相关
运行时文档。只有形成或改变架构、缓存策略等长期决策时才新增 ADR。

## 初步数据及其边界

在临时用户目录、自动化 `--disable-gpu` 环境中曾采集到：

- 空闲 10 秒共 601 帧，平均 16.67ms，P95 16.70ms，最大 16.8ms。
- 没有超过 20ms 或 50ms 的帧，也没有 Long Task。
- 空闲时没有天气粒子节点。
- 3640 × 1920 虚拟桌面下，Browser、GPU、Utility、Tab 进程工作集总和约
  649MB；私有内存总和约 243MB。

这些数据只能证明自动化场景中没有明显的空闲渲染卡顿，不能直接代表安装包、
真实显卡、其他刷新率或用户长期运行时的表现。Windows 工作集还可能包含进程间
共享页面，因此后续内存判断以分进程私有内存和总私有内存为主，工作集仅作辅助。

## 统一测量协议

后续性能结论必须遵循同一协议：

- 记录应用版本、Electron 版本、dev/packaged 构建类型、操作系统、CPU、GPU、
  驱动、电源模式，以及每块显示器的分辨率、缩放和刷新率。
- 使用隔离的测试 userData，不读取或修改真实用户配置。普通场景使用新建 profile；
  热启动和缓存 A/B 使用可跨多次启动复用、完成后可删除的专用测试 profile。
- 场景必须通过固定 QA 入口确定性触发，不能依赖随机移动、实时天气或人工等待来
  决定采样内容。
- 每个场景先预热至少 5 秒，再采样至少 30 秒，并独立重复至少 3 次；启动 A/B
  至少执行 5 对交替顺序的样本，避免缓存预热和执行顺序造成偏差。
- 保存原始 JSON 和 Markdown 摘要。摘要报告中位数、P95、最大值、重复样本波动，
  不用单次最佳结果作决策。
- 帧间隔预算按显示器刷新率计算；60Hz 时以 16.67ms 为目标预算、20ms 为 P95
  警戒线。其他刷新率使用 `1.2 × 理论帧间隔` 作为对应警戒线，同时保留超过
  20ms/50ms 的帧数、连续掉帧和 Long Task 统计。

## 依赖关系

```text
性能采样工具
  └─> 可复现基线报告与问题分流
        ├─> 天气粒子专项优化（仅在天气场景超标时）
        ├─> 启动缓存路径优化（仅在清缓存等待被证实时）
        ├─> 空闲帧率降档评估（仅在真实 CPU/耗电超标时）
        └─> 透明窗口内存可行性研究
              └─> 小窗口/动态窗口架构的独立实施计划
```

## 多 Agent 并行执行模型

### 并行边界

并行单位是“同一个原子任务中的互不重叠子包”，不是同时实施多个性能问题。
任务 3、4、5、6 即使同时达到分流门槛，也必须由主代理一次只激活其中一项；
当前任务完成测试、复测、文档和审查闭环后，才能激活下一项。

执行时最多使用 1 个主代理和 3 个下位编码代理。下位编码代理默认使用
`gpt-5.6-terra`、`medium` 推理强度；如果子包只涉及机械测试或文档整理，可降为
`low`。下位代理不负责性能结论、架构决策、最终合并或发布判断。

### 角色与职责

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 主代理 | 冻结任务契约、确定性能门槛、处理关键边界、分配文件、集成补丁、运行最终验证并作出是否通过的结论 | 不把性能分流、架构取舍或最终审查交给下位代理 |
| 编码代理 A | 在允许文件内完成核心实现与最小聚焦测试 | 不修改共享入口、架构文档或未授权文件 |
| 编码代理 B | 编写独立测试、测试夹具或 Electron/Playwright 验证脚本 | 不为了让测试通过而修改验收标准或生产行为 |
| 编码代理 C | 准备性能复测脚本、样本校验、人工回归清单或隔离原型 | 不使用真实 userData，不自行解释性能结果为最终结论 |
| 预审代理 | 在编码结束后进行只读的正确性、边界和测试覆盖检查 | 不直接合并、不替代主代理最终审查 |

编码代理和预审代理可以复用同一个并发槽位：前三个代理完成并停止后，再启动一个
新鲜上下文的预审代理。主代理始终保留最终决定权。

### 主代理保留的关键工作

以下工作不得完全委派；主代理必须亲自设计、检查并在必要时完成敏感接线：

- 新 QA 入口、`app.*ForQA` hook、main/preload IPC、sender 授权和 userData 隔离。
- 性能 JSON schema、统计口径、刷新率预算、异常样本处理和任务分流结论。
- `pet-asset` 缓存失效契约、版本指纹和升级正确性策略。
- `displayBounds.js`、`displayFit.js`、多屏/DPI、macOS Space/fullscreen 和透明窗口
  架构边界。
- 游戏循环调度、休眠恢复、时间跳变保护以及随机移动/互动的唤醒语义。
- 对下位代理补丁的集成、冲突处理、最终 diff 审查、测试与性能复测。

### 子任务包格式

主代理在启动任何编码代理前，必须给出完整任务包：

1. 单一目标和明确的非目标。
2. 允许修改的文件清单、只读参考文件和禁止修改的共享文件。
3. 已冻结的输入/输出、CLI、JSON schema 或模块接口。
4. 必须新增或更新的聚焦测试，以及代理应运行的最小验证命令。
5. 完成条件、回报格式和遇到契约冲突时立即停止的条件。

每个代理完成后必须报告：修改文件、行为变化、运行过的测试、未运行的验证、假设和
剩余风险。代理不得自行 commit、push、删除用户文件或顺手重构任务范围外代码。

### 文件并发规则

- 同一轮中两个编码代理不得修改同一个文件。
- `package.json`、`CHANGELOG.md`、`docs/structure.md`、ADR、`main.js`、`preload.js`、
  `src/main/AppLifecycle.js` 和 `src/app.js` 默认由主代理持有；确需委派时，该文件在
  当前轮只能分配给一个代理，主代理仍逐行复审。
- 能使用隔离 worktree 时，每个编码包使用独立 worktree；不能隔离时，只允许对
  明确互斥的文件并行写入。存在文件交叠时，改为并行只读调查、串行写入。
- 主代理在集成前先保存并检查每个代理的独立 diff；一次只集成一个补丁，并在每次
  集成后运行该补丁对应的聚焦测试。

### 各任务的并行分工

| 原子任务 | 主代理负责 | 可并行交给下位代理 |
| --- | --- | --- |
| 任务 1：采样工具 | 冻结 CLI/JSON schema、QA 接口、进程指标口径；处理敏感 QA 接线和最终集成 | A：统计与报告模块；B：Electron/profile 启动器和测试；C：场景驱动、样本校验与使用文档 |
| 任务 2：基线与分流 | 执行或监督正式采样，处理异常样本，亲自作出四个分流结论并签署报告 | A：校验原始 JSON；B：独立复算摘要；C：复现代表场景和整理环境信息，均不得修改结论 |
| 任务 3：天气优化 | 亲自读 trace 并选择脚本、布局或合成方向；集成后执行同协议复测 | A：被证实瓶颈的最小实现；B：天气回归测试；C：复测脚本和人工视觉矩阵 |
| 任务 4：缓存优化 | 冻结版本失效策略和升级安全契约；审查协议/main 进程边界 | A：缓存策略实现；B：Electron 升级缓存集成测试；C：持久测试 profile 的 A/B 启动脚本 |
| 任务 5：窗口研究 | 冻结行为约束、内存口径和取舍门槛；决定采用或拒绝并撰写 ADR | A：小窗口跟随隔离原型；B：动态窗口范围隔离原型；C：多屏/DPI/Space 回归矩阵与内存复测 |
| 任务 6：空闲降档 | 冻结状态机、全部唤醒源和时间语义；亲自审查/完成 `src/app.js` 接线 | A：调度器模块与单元测试；B：唤醒源和时间跳变测试；C：CPU/耗电复测及长时间观察脚本 |

### 每个原子任务的执行波次

```text
波次 0（主代理，串行）
  └─> 检查工作树与用户改动 → 冻结契约/文件所有权 → 写出任务包

波次 1（最多 3 个下位代理，并行）
  ├─> 实现包
  ├─> 测试/验证包
  └─> 复测/文档准备包

波次 2（主代理，串行集成）
  └─> 逐补丁读 diff → 逐个集成 → 每次运行聚焦测试

波次 3（新鲜上下文预审代理，只读）
  └─> 检查正确性、架构边界、遗漏测试和可疑性能结论

波次 4（主代理，最终审查）
  └─> 处理预审意见 → 全量验证 → 同协议复测 → 文档闭环 → 最终通过/退回
```

### 主代理最终审查门槛

主代理必须亲自完成并记录以下检查，任何一项失败都退回对应编码包：

- 先审测试，再按正确性、可读性、架构、安全、性能五个维度逐文件审查实现。
- diff 只包含任务包允许的文件和必要变更，没有无关格式化、推测性抽象或孤儿代码。
- main/preload/renderer 边界、IPC sender 校验、QA 入口、点击穿透、拖拽暂停、
  `scaleRatio`、雷暴禁风和游戏循环 `try/catch` 等适用约束仍然成立。
- 聚焦测试、`npm test`、Electron 冒烟和任务要求的人工/平台验证全部有结果；涉及
  builder 或签名时再运行仓库规定的构建、安装包和签名检查。
- 性能改动具有同设备、同构建、同场景的前后数据，收益超过波动且没有其他场景
  退化；否则回滚生产改动，只保留测量结论。
- `CHANGELOG.md` 的 `Unreleased` 中文条目位于唯一正确分类下，没有重复标题；
  `docs/structure.md`、性能报告和必要 ADR 与最终行为一致。
- 只有主代理可以宣布任务完成；commit/push 仍需用户授权，并使用项目规定的
  `push.ps1`/`push.sh` 安全流程。

## 阶段 1：建立可复现基线

### 任务 1：新增 Electron 性能采样工具

**说明：** 复用现有 Playwright Electron 冒烟工具的临时 userData 隔离方式，
新增专用性能命令。工具负责确定性触发空闲、行走、重雨、强风、高温和雷暴场景，
并支持单屏、多屏、高 DPI、默认 GPU 和 `--disable-gpu` 模式。工具只采集数据，
不在本任务中修改生产渲染逻辑。

**验收标准：**

- [x] 输出环境元数据、实际帧间隔、P50/P95/最大值、超过警戒线及 20ms/50ms
  的帧数、连续掉帧、Long Task、DOM/粒子数，以及各 Electron 进程的区间 CPU、
  私有内存和工作集。
- [x] 支持新建隔离 profile 和复用专用测试 profile；退出后不写入真实用户配置、
  皮肤选择或正常应用数据目录。
- [x] 场景、预热、采样时长和重复次数可配置且有安全默认值，原始 JSON 能区分
  dev/packaged、GPU/`--disable-gpu` 和各天气场景。
- [x] 单元测试覆盖统计计算、参数校验和 userData 隔离；性能门槛不写成易受机器
  抖动影响的普通单元测试断言。

**验证：**

- 新增采样工具的聚焦测试。
- `npm test`
- `npm run qa:electron:smoke`（自动化环境须清除 `ELECTRON_RUN_AS_NODE`）。
- 使用最短采样配置验证 JSON schema、进程归类和临时 profile 清理。

**执行结果（2026-07-23）：** 聚焦测试 30/30、全量测试 658/658 和 Electron
冒烟均通过；最短采样已验证默认 GPU 与 `--disable-gpu` 分支，六个场景均能生成
renderer/进程原始样本及逐场景汇总，临时 profile 在退出后已清理。正式 30 秒 ×
3 次基线仍属于任务 2，不以本任务的短采样代替。

**依赖：** 无
**预计范围：** 中等，涉及 `tools/`、`package.json`、测试和性能文档。

### 任务 2：采集可复现基线并完成问题分流

**说明：** 使用任务 1 的工具，按照统一测量协议分别采集 dev 与 packaged、真实
GPU 与 `--disable-gpu` 数据。报告保存到 `docs/performance/`，明确记录命令、环境、
原始结果位置、异常样本处理理由和最终是否进入各条件任务。

**验收标准：**

- [x] 目标 Windows 设备启用 GPU 后，每个核心场景完成至少 3 次、每次至少
  30 秒的采样；自动化 `--disable-gpu` 数据单独呈现，不与真实 GPU 结果合并。
- [x] dev 与 packaged 均有空闲和核心天气基线；私有内存为主要内存指标，工作集
  仅作辅助且不把共享页面解释为应用独占成本。
- [x] 报告对天气、启动、内存和续航候选问题逐项给出“进入后续任务”或“停止”
  结论，并引用具体样本，不使用“明显”“不可接受”等未量化表述。

**执行结果（2026-07-23）：** 四组正式主矩阵、启动探针、三次五分钟空闲采样和
强风代表场景复现已完成；正式主矩阵、空闲样本及三次序列控制复现通过协议校验与
独立复算。首次单次强风复现是触发协议修正的诊断样本，不适用要求至少重复 3 次的
正式验证器；其未落入首批窄区间后，按计划修正为同批空闲对照并完成三次序列控制
复现。两批每次强风均超过 CPU 相对 +20% / 绝对 +1pp 门槛。量化分流见
`docs/performance/2026-07-23-windows-baseline.md`，Task 2 已签署。

**分流门槛：**

- 天气：任一场景在至少 2 次重复中超过对应刷新率 P95 警戒线、产生可复现的
  50ms Long Task，或进程 CPU 相比空闲同时出现至少 20% 的相对增幅和 1 个百分
  点的绝对增幅，才进入任务 3。
- 启动：`clearCache()` 中位耗时达到 100ms，或占 `createWindow` 到
  `did-finish-load` 中位时间的 10% 以上，才进入任务 4。
- 内存：仅当分进程数据表明窗口尺寸与私有内存稳定相关，才进入任务 5。
- 续航：目标设备连续 5 分钟空闲时，Electron 进程组 CPU 中位数高于 2%，或系统
  能耗工具持续显示高于“低”档，且重复 3 次仍成立，才进入任务 6。

**验证：**

- 复核原始 JSON 与 Markdown 汇总计算一致。
- 在相同环境重跑一个代表场景，结果应落入已记录波动区间；否则先修正采样协议。
- 本任务只形成报告和分流结论，不修改生产代码。

**依赖：** 任务 1
**预计范围：** 小，性能报告及必要的采样配置。

## 阶段 2：针对已证实的问题优化

### 任务 3：天气粒子层专项优化（条件执行）

**触发条件：** 任务 2 的天气分流门槛成立。

**说明：** 先用 trace 区分脚本执行、样式/布局和 GPU 合成成本，再选择最小修复。
如果瓶颈来自脚本，再减少 `WeatherParticleLayer` 的每帧数组创建、子节点枚举或
重复样式写入；如果瓶颈来自合成，再针对 trace 指向的 `mask`、动态
`clip-path`、`blur` 或阴影降级。当前“状态未变化时不重建粒子层”是必须保留的
既有行为，不作为本任务新增成果。

**验收标准：**

- [x] 性能报告明确指出瓶颈属于脚本、样式/布局或合成中的哪一类，并让代码改动
  只针对被证实的原因。
- [x] 优化后目标天气场景的超标指标至少改善 20%，或恢复到对应刷新率预算以内；
  其他场景不能出现超过测量波动区间的退化。
- [x] 保留粒子数量上限、天气密度、`scaleRatio`、雷暴禁风、互动合并、低动态
  效果和 `prefers-reduced-motion` 行为。

**验证：**

- `test/weatherParticleLayer.test.js`
- `test/weatherParticleStability.test.js`
- 全量 `npm test`
- 使用任务 2 的同场景、同设备、同构建进行前后复测。
- 人工检查重雨、强风、高温、雷暴、双人互动和减弱动态效果。

**执行结果（2026-07-23）：** 瓶颈定位为 GPU 合成（占强风 CPU 增量 46.6%，
`mask-image`、`clip-path` 动画和 `drop-shadow`）和 JS 脚本执行（占增量 37.4%，
每帧 `Array.from`/`.map`/`.filter` 分配和无条件 DOM style 写入）。已完成的

## 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 自动化环境禁用 GPU，数据不代表用户机器 | 报告中标注环境；关键结论必须在真实 GPU 和 packaged 构建上复测。 |
| 单次采样或后台负载造成误判 | 固定环境、预热和场景，至少重复 3 次并报告波动，不使用单次最佳值。 |
| 工作集重复计算共享页面 | 以分进程及总私有内存为主，工作集仅作辅助。 |
| 新临时 profile 掩盖热启动缓存成本 | 缓存 A/B 使用可跨多次启动复用的专用测试 profile。 |
| 缓存优化导致更新后显示旧皮肤 | 先证明清缓存是瓶颈；以应用或资产清单版本失效，并增加真实 Electron 升级缓存测试。 |
| 小窗口架构破坏桌宠体验 | 只做隔离可行性验证，同时满足绝对和相对收益门槛才进入正式实现。 |
| 空闲循环优化造成状态遗漏 | 明确低频状态与全部唤醒源，覆盖休眠恢复、互动、天气、显示器和存档测试。 |

## 执行顺序

严格按“任务 1 → 任务 2 → 根据分流结果选择一个条件任务”的顺序执行。任务 3、
4、5、6 之间没有默认全部实施的含义；每次只处理其中一项，并在测试、同协议性能
复测、`CHANGELOG.md` 和相关文档闭环后，再决定是否进入下一项。任务 5 若建议改变
窗口架构，必须先提交新的独立实施计划，不在本计划中直接扩展范围。

主代理串行集成 → 新鲜上下文预审 → 主代理最终审查”的波次执行。并行用于缩短同一
任务的实现时间，不改变任务之间的依赖关系，也不允许绕过任何测试或文档闭环。
