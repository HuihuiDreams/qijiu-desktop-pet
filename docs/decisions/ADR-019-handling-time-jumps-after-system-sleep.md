# ADR-019: 处理系统休眠后的时间跳跃 (Handling Time Jumps After System Sleep)

## 状态 (Status)
Accepted

## 日期 (Date)
2026-05-10

## 背景 (Context)
用户反馈在电脑进入睡眠/休眠模式（Sleep Mode）很长时间后唤醒，发现桌宠的属性数值没有变化，且没有触发预期的“离线归来”欢迎对白。尽管应用在休眠期间一直保持开启状态，但时间流逝的影响未能正确体现。

## 问题分析 (Problem)
1. **循环暂停**：在浏览器/Electron 环境中，当电脑进入休眠时，`requestAnimationFrame` 会被挂起，游戏主循环停止运行。
2. **时间跳跃**：当电脑唤醒时，`performance.now()` 会返回当前时间，导致唤醒后的第一帧 `deltaMs`（当前时间与上一帧时间的差值）变得极其巨大（可能是数小时）。
3. **逻辑失效**：
   - 现有的 `NurtureSystem.update` 使用 `if` 判断而非 `while` 循环处理衰减，导致无论跳跃多久，单帧内只执行一次衰减。
   - 欢迎对白逻辑原本只写在 `app.js` 的初始化（Load）阶段，未考虑到应用不关闭直接从休眠中唤醒的情况。
   - 巨大的 `deltaMs` 直接传递给物理/运动系统会导致物体瞬间位移过大（暴走）。

## 决策 (Decision)
为了修复此问题并增强系统的鲁棒性，做出以下修改：

1. **睡眠唤醒检测**：在 `app.js` 的 `gameLoop` 中增加逻辑，若 `deltaMs > 60000`（1分钟），判定为经历了系统休眠或挂起。
2. **即时离线结算**：在检测到跳跃时，立即调用 `applyOfflineDecay(offlineMs)` 模拟离线时长结算属性。
3. **触发动态欢迎语**：在休眠唤醒后，根据跳跃时长（每 2 小时为一个时辰）动态触发“你走了几个时辰”的欢迎对白。
4. **时间压制 (Time Capping)**：结算完跳跃时间后，强行将该帧的 `deltaMs` 重置为 `16ms`（约 1 帧），确保后续的运动系统和动画系统不会因巨大的时间差而崩溃。
5. **即时保存**：唤醒后立即执行 `timeSystem.save()`，确保离线结算后的数值被持久化。
6. **累加器鲁棒性**：在 `TimeSystem.update` 中使用取模运算 (`%=`) 处理 `saveAccumulator`，防止在极端时间跳跃下残留巨大值导致连续帧强制存档。

## 替代方案 (Alternatives Considered)

### 只让 `NurtureSystem.update` 用 `while` 消化巨大 `deltaMs`
- 优点：改动集中在数值系统内，能让饥饿、灵力和心情按时间补算。
- 缺点：运动、动画、欢迎对白和保存逻辑仍会收到异常大的单帧时间差，无法完整解决唤醒后的表现问题。
- 结论：拒绝。休眠唤醒是跨系统事件，需要在 game loop 边界统一识别和压制。

### 完全忽略超过阈值的 `deltaMs`
- 优点：可以避免桌宠瞬间位移过大，运动系统最稳定。
- 缺点：会丢失休眠期间的养成时间，用户仍看不到离线衰减和欢迎对白。
- 结论：拒绝。稳定性不能以牺牲养成时间一致性为代价。

### 依赖应用重启时的离线结算
- 优点：复用已有启动流程，不需要处理运行中休眠。
- 缺点：用户只睡眠/唤醒电脑但不退出应用时不会触发该流程，正是本问题的复现路径。
- 结论：拒绝。运行中唤醒必须和关闭后重启保持一致的时间体验。

## 影响 (Consequences)
- **优点**：完美解决了电脑不关机、只进入休眠模式下的养成体验断档问题，使“离线衰减”和“欢迎对白”在所有场景下表现一致。
- **性能**：由于使用了专门的离线结算函数，即使跳跃时间很长，计算也是瞬间完成的，不会造成掉帧。
- **稳定性**：通过 `deltaMs` 压制，避免了系统唤醒后桌宠瞬间“飞走”的潜在 Bug。
