# ADR-011: 增加隐藏/显示桌宠及游戏逻辑暂停机制

## Status
Accepted

## Date
2026-05-01

## Context
随着桌面宠物的完善，用户有时可能需要专注于工作，希望临时将桌宠从屏幕上移开，但又不希望完全退出程序（比如希望继续挂机，或者觉得每次重新打开程序较麻烦）。因此，系统托盘菜单需要提供一种隐藏和恢复显示桌宠的方法。

我们需要考虑：
1. **渲染层还是窗口层隐藏**：如果直接调用 `mainWindow.hide()`，整个无边框透明窗口会被隐藏。这虽然可行，但更细粒度的控制是将隐藏的职责交给渲染进程。
2. **隐藏时的状态流失**：如果只是视觉上隐藏（如 `display: none`），宠物的数值（饱腹、灵力等）在后台依然会因为真实时间的流逝而自然衰减，这对用户不公平（不可见的情况下依然在消耗属性）。
3. **菜单交互的直观性**：菜单栏的文字需要动态响应当前状态，隐藏时显示“显示桌宠”，显示时显示“隐藏桌宠”。

## Decision
1. **采用渲染层控制与 IPC 通信**：在主进程中维护一个 `petHidden` 的状态变量，并在系统托盘菜单被点击时，触发 IPC 消息 `toggle-pet-visibility` 发送给渲染进程。
2. **菜单动态重建**：将创建托盘菜单的逻辑抽象出 `buildTrayMenu()` 函数，每次点击隐藏/显示菜单项时，重新调用此函数并 `tray.setContextMenu()` 以便动态更新菜单文字。
3. **隐藏即暂停 (Hide means Pause)**：在 `app.js` 接收到隐藏指令时，除了对 `#pet-stage` 设置 `display: none`，还会**同步切换全局 `isPaused` 状态**。隐藏期间游戏循环跳过逻辑更新，数值不会自然衰减，也不会触发任何闲聊气泡。

## Alternatives Considered
### 直接调用 `mainWindow.hide()`
- **Pros**: 主进程直接搞定，不需要 IPC，实现非常简单。
- **Cons**: 无法轻松地暂停游戏逻辑，意味着渲染层依然在执行 requestAnimationFrame 和数值衰减计算；如果我们希望后续有某些 UI（例如独立的状态监控小面板）在宠物隐藏时依然保留，这种直接隐藏整个 BrowserWindow 的方式就缺乏灵活性。
- **Rejected**: 考虑到资源占用和游戏逻辑暂停的需求，采用渲染层控制更好。

## Consequences
- 用户可以在不退出程序的情况下随时隐去宠物，专注于工作。
- 隐藏期间，游戏循环不执行核心逻辑，极大降低了后台资源消耗，并且保护了宠物的数值不被无谓消耗。
- 主进程的 `main.js` 增加了一定程度的菜单状态管理复杂性（需要重建菜单）。
