# ADR-023: 稳定静止到行走的精灵帧切换

## Status
已接受 (Accepted)

## Date
2026-05-13

## Context
用户反馈角色从静止状态切换到行走状态时，刚开始的几帧会出现类似“闪眼睛”的视觉跳变，走了几步之后又会恢复正常。

排查后发现该现象主要来自两个叠加因素：

1. `MovementSystem` 在 `idle` 切换为 `walking` 的当帧只设置了新目标点，真正的 `direction` 更新发生在下一轮 `moveTowardTarget()` 中。因此首个行走渲染帧可能仍使用旧朝向的行走帧，下一帧再切换到正确朝向。
2. `SpriteView._render()` 在每次切换图片资源时使用 `innerHTML` 重建 `<img>` 节点。行走动画首次播放时，浏览器需要加载和解码多张走路帧图，首轮更容易出现短暂闪烁；等图片进入缓存后，视觉问题自然减轻。

这类问题属于帧切换稳定性，不应通过提高 FPS、增加过渡滤镜或延长动画时间来掩盖，否则会让角色动作变糊或增加渲染负担。

## Decision
在现有 `SpriteView` DOM 精灵架构内做最小但根因导向的修复：

1. **行走前先确定朝向**
   - 在 `MovementSystem` 从 `idle` 切换到 `walking` 前，根据新目标点与当前位置的水平关系立即设置 `pet.direction`。
   - 保证首个行走帧就使用正确的 `walkingLeft` / `walkingRight` 资源。

2. **预加载角色帧图**
   - 在 `SpriteView.attach(pet)` 时收集该角色的静止图、`sprites` 中的多帧序列图，以及 `imageMap` 中的特殊状态图。
   - 通过 `new Image()` 提前触发浏览器加载与解码路径，并把引用保存到 `pet._sv_preloadedImages`，避免被垃圾回收过早释放。

3. **复用 `.pet-image` 节点**
   - `SpriteView._render()` 渲染图片时不再用 `innerHTML` 销毁并重建 DOM。
   - 若 `.pet-image` 已存在，则只更新同一个节点的 `src` 和 `alt`。
   - 只有从 emoji 回到图片时才创建新的 `<img>` 节点。

4. **测试保护方向切换时序**
   - 新增 `test/movementSystem.test.js`，验证宠物从 `idle` 进入 `walking` 的同一轮更新中，朝向已经与目标方向一致。

## Alternatives Considered
### 继续使用 `innerHTML`，只依赖浏览器缓存
- **优点：** 代码改动最小。
- **缺点：** 首轮加载/解码仍会闪，且每次换帧都销毁 DOM 节点，和 ADR-012 中“避免高频 DOM 重建”的方向相悖。
- **结论：** 拒绝。缓存只能缓解后续播放，不能稳定首次切换。

### 给行走状态增加淡入或 cross-fade
- **优点：** 可以视觉上遮盖跳帧。
- **缺点：** 会让像素/立绘帧动画变糊，且增加额外图层和透明度动画，不能解决旧朝向首帧的问题。
- **结论：** 拒绝。该问题应先修正状态和资源切换时序。

### 改用 Canvas 或精灵图 atlas
- **优点：** 对大量精灵和高帧率动画更可控。
- **缺点：** 当前同屏角色数量极少，改造成本远高于收益；还会牵动 CSS 滤镜、拖拽命中、鼠标穿透和互动覆盖层。
- **结论：** 暂不采用。保留为未来大量角色或复杂动画时的升级方向。

## Consequences
- 静止切换到行走时，首帧朝向与目标方向一致，减少脸部/眼睛方向突变。
- 行走帧首次播放前更可能已经进入浏览器缓存，降低首轮加载闪烁。
- 高频帧切换不再反复创建 `<img>` DOM 节点，减少垃圾回收和布局扰动。
- `SpriteView` 会为每只宠物保留少量预加载 `Image` 引用，带来很小的内存常驻成本；当前素材数量有限，该成本可接受。
- `MovementSystem` 增加了 CommonJS 导出，仅用于 Node 测试；浏览器环境下不会改变全局类的使用方式。
