# ADR-017: 引入 SpriteView 重构多帧动画系统

## Status
已接受 (Accepted)

## Date
2026-05-06

## Context
此前，桌面宠物的视觉展示逻辑由 `PetAnimations.js` 处理，它直接通过替换 emoji 字符串或静态图片路径来操作 `.pet-body` 的 DOM 内容。随着多帧美术资产（例如沈九的 4 帧行走动画）的引入，现有的静态图片映射机制已无法满足需求。

在旧架构中，`PetAnimations` 和 `PetRenderer` 之间的职责边界逐渐模糊，导致我们很难在不大幅增加主游戏循环复杂度的情况下，引入按需脏标记渲染、帧率控制 (fps) 和基于状态的动画循环。

## Decision
创建一个专门的 `SpriteView.js` 类来接管 `.pet-body` 的视觉渲染层，彻底取代 `PetAnimations.js`。

`SpriteView` 类将具备以下特性：
1. 接受宠物配置中可选的 `sprites` 对象（例如：`walking: { frames: [...], fps: 4 }`）。
2. 根据配置的 FPS，内部管理帧索引和基于 `deltaMs` 的时间计算。
3. 若某状态未提供多帧 `sprites` 配置，则自动平滑回退至原有的静态图片映射或 emoji 映射。
4. 引入脏标记（`_sv_lastResource`），确保仅在视觉资产实际发生改变时才更新 DOM，以最大程度减少浏览器的重排/重绘开销。

## Alternatives Considered
### 直接扩展 `PetAnimations.js`
- **优点：** 代码结构改动较小。
- **缺点：** 该类实际上已经退化为一个静态数据字典，而非主动渲染器。若强行加入帧计时逻辑，将导致职责混淆、类文件极度臃肿。

### 将渲染逻辑合并至 `PetRenderer.js`
- **优点：** 将所有 DOM 操作集中在一处。
- **缺点：** `PetRenderer` 目前已经承担了 CSS 类切换、坐标变换、拖拽事件、鼠标穿透以及双人互动覆盖层的管理。再塞入逐帧动画状态机将严重违反单一职责原则，使其变得难以维护。

### 使用 HTML5 Canvas 替代 DOM `<img>`
- **优点：** 处理高帧率精灵图渲染时性能更好。
- **缺点：** 需要重写整个鼠标穿透机制、现有的 CSS 滤镜特效（发光/阴影）以及交互覆盖层。鉴于目前同屏精灵数量极少，且已经使用了 CSS 3D transforms 硬件加速，当前的 DOM 方案在性能上已完全绰绰有余，重写成本过高。

## Consequences
- **清晰的资产工作流：** 现在可以直接在 `config.js` 的 `sprites` 属性中定义多帧序列动画。
- **向下兼容：** 现有的单帧图片和 emoji 会通过回退机制继续完美运行，无需立刻替换所有美术素材。
- **性能保障：** 只有在切换动画帧时才更新 DOM，维持了应用的高性能运行。
- **代码废弃：** `PetAnimations.js` 的历史使命已结束，现已完全从应用的主循环中剔除。
