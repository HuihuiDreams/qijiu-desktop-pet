# ADR-022: 多显示器支持边界

## 状态 (Status)
Accepted

## 日期 (Date)
2026-05-12

## 背景 (Context)
桌宠应用正在逐步支持多显示器场景。当前已经拆出了独立状态面板窗口，并新增了 `displayBounds.js` 用于计算多显示器虚拟桌面边界。主进程也会监听显示器插拔和分辨率变化，以便在显示环境变化时重新调整窗口。

但当前用户可见能力并不是完整的“桌宠跨屏活动”：

- 状态面板窗口可以拖曳到副屏使用。
- 岳七和沈九本体目前只能在主屏范围内活动。
- 桌宠暂不支持主动走到副屏，也暂不支持被拖曳到其他显示器。

如果文档把当前能力描述为“多显示器全覆盖支持”，会误导用户和后续开发者。现阶段更准确的说法是：多显示器基础设施已开始引入，但桌宠活动范围仍限制在主屏。

## 决策 (Decision)
将多显示器支持拆成两个层级记录和交付。

第一层：已支持的能力。

- 独立状态面板窗口允许用户拖曳到副屏。
- 主进程保留多显示器边界计算工具和显示器变化监听，作为后续跨屏能力的基础设施。
- README 和 CHANGELOG 只描述已验证的用户可见行为，不声明桌宠已经支持跨屏活动。

第二层：暂不支持的能力。

- 桌宠本体移动范围仍以主屏为边界。
- 拖曳桌宠时不承诺跨显示器坐标转换。
- 自动行走、互动距离、位置存档和重置位置都不按完整虚拟桌面语义处理。

未来如果要实现完整跨屏桌宠，需要作为单独功能设计和验证，而不是只依赖主窗口覆盖虚拟桌面。

## 备选方案 (Alternatives Considered)

### 继续宣称多显示器全覆盖支持
- Pros: 文档看起来更完整，也能表达架构方向。
- Cons: 与实际体验不符；用户会期待小人能走到或拖到副屏，测试和验收标准也会被错误放大。
- Rejected: 文档必须优先反映真实行为。

### 立即实现桌宠跨屏活动
- Pros: 多显示器体验最完整。
- Cons: 需要一起处理渲染坐标、拖曳坐标、显示器负坐标、高 DPI 缩放、位置存档、重置逻辑、互动碰撞和点击穿透边界，风险超过当前文档补充的范围。
- Rejected: 应拆成独立功能迭代。

### 只支持状态面板跨屏，不保留主窗口虚拟边界基础设施
- Pros: 当前能力更简单，边界更清晰。
- Cons: 后续实现桌宠跨屏时仍需重新引入多屏边界计算；现有工具和测试已经能作为低风险基础。
- Rejected: 保留基础设施，但不夸大它带来的用户能力。

## 影响 (Consequences)
- 对外文档需要明确区分“状态面板可跨屏”和“桌宠本体可跨屏”。
- CHANGELOG 中应避免使用“多显示器全覆盖支持”这类完成式表述，除非桌宠本体也已经通过跨屏行走和拖曳验证。
- 后续跨屏功能应至少验证：
  - 主屏右侧、副屏左侧和负坐标显示器布局。
  - 不同缩放比例显示器下的拖曳坐标。
  - 自动行走边界、重置位置和位置存档。
  - 隐藏/显示、单实例唤起和置顶守卫在副屏场景下的行为。
