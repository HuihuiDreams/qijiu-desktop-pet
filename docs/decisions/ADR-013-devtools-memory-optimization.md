# ADR-013: 移除自动挂载 DevTools 以优化基础内存占用

## 状态 (Status)
Accepted

## 日期 (Date)
2026-05-01

## 背景 (Context)
尽管实施了 ADR-012 中的渲染层DOM优化，Electron 应用的基础内存占用依然高达 ~300MB。在考虑向 Tauri 这种轻量级框架迁移之前，我们对主进程的启动逻辑进行了诊断。
发现 `main.js` 中保留了调试期的设定：`mainWindow.webContents.openDevTools({ mode: 'detach' });`
在生产模式下，即使 DevTools 窗口是分离或隐藏状态，Chromium 也会为开启了调试工具的 `webContents` 维护一个极其庞大的调试上下文（包含所有的源码映射、DOM树快照、网络记录器等），这会导致无意义且巨大的内存开销。

## 决策 (Decision)
移除在启动时自动打开 DevTools 的代码。
保留开发态托盘菜单中的 "🛠️ 开发者工具" 按钮，将其作为按需开启调试的唯一入口。
该入口仅在 `!app.isPackaged` 时显示，安装包版本不展示调试菜单项。

## 替代方案 (Alternatives Considered)
- **迁移至 Tauri**: 考虑过彻底放弃 Electron 以换取更小的内存占用。但考虑到这需要重写整个进程间通信和打包流程，成本过高。通过排查 Electron 配置问题，我们发现了 DevTools 的巨大开销。

## 影响 (Consequences)
- **立竿见影的内存收益**：渲染进程的内存占用显著下降近 100MB，稳定在 200MB 出头。
- **开发体验**：开发者在测试时不再自动弹出调试窗，需要手动从托盘右键开启。
- **安装版体验**：普通用户不会在托盘菜单中看到 DevTools 入口，菜单只保留实际可用的软件功能。
- **推迟了架构迁移需求**：由于内存占用回落到健康的区间，极大地缓解了向 Tauri 迁移的技术压力，使得团队当下可以继续专注于核心游戏玩法和美术资产的开发。

## 2026-05-22 后续复盘：图片内存优化的边界

在 2026-05-22 的内存优化中，我们进一步排查了默认皮肤图片资源对 Electron 总内存的影响。最终采取的策略是：

1. 保留 `SpriteView` 的全套图片预加载策略，避免状态切换时临时解码导致的闪烁。
2. 将默认皮肤运行时资源从 PNG 切换为 WebP。
3. 将运行时 WebP 控制在最大边 256px。
4. 保留全分辨率 WebP 备份在 `docs/source-assets/default-webp-fullres/`，运行时只加载 `src/assets/default/**/*.webp`。
5. 保留 emoji fallback：图片加载失败时仍回退到角色 emoji，而不是文本占位。

优化后的默认运行时图片资源规模约为：

- 文件数量：41 张
- 磁盘体积：约 1.82 MB
- 全部解码为 RGBA 后的理论内存：约 9.54 MB
- 最大边：256px

这次复盘的重要结论是：图片资源优化是有效的，但它已经不是资源管理器中 200MB-300MB 级别占用的主因。压缩和缩放图片后，Windows 资源管理器里的 Electron 总内存变化不明显，主要原因是剩余大头来自 Electron/Chromium 基础开销、多个子进程、透明置顶窗口、全虚拟桌面尺寸的窗口缓冲区与合成层，而不是图片解码内存。

因此，后续 agent 不应继续把主要精力放在反复压缩默认图片资源上。除非新增皮肤资源明显超过当前规模，否则图片侧的收益会很有限。

## 后续建议

如果还需要显著降低资源管理器中的总内存，下一步应优先评估窗口架构，而不是继续压图片：

- 当前 `main.js` 使用覆盖整个虚拟桌面的透明 `BrowserWindow`。这种设计对多屏、拖动、点击穿透和全局桌宠体验简单稳定，但会带来较高的 Chromium 合成与窗口缓冲区成本。
- 更可能带来明显内存下降的方向是“小窗口跟随宠物”或“动态缩小透明窗口范围”。这需要重新验证拖动、点击穿透、多屏边界、气泡、互动覆盖层和闪烁问题。
- 不建议恢复“只持有 idle 一张图，其余状态按需加载”的策略。该策略可能降低图片引用数量，但会增加状态切换时的解码/加载风险，历史上已经担心过视觉闪烁；当前图片总解码量已经很小，收益不足以抵消体验风险。
- 开发模式下的资源管理器数据不能直接代表安装包表现。做下一轮判断时，应同时比较 dev 启动和 packaged 启动的进程内存。
