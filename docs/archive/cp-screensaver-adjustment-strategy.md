# CP 屏保后续修改策略（意见汇总）

> 状态：已实施（S-01 / S-02 / S-03 全部落地）。
>
> 基线设计：[CP 屏保实施计划](./cp-screensaver-plan.md)；现有决策：[ADR-044](../decisions/ADR-044-cp-screensaver-session.md)。
> 实施计划：[CP 屏保后续修改实施计划](./cp-screensaver-adjustment-implementation-plan.md)。

## 已实施的落实情况

- **S-01**：`activeWindowProvider` 的 PowerShell 采样现通过 `MonitorFromWindow` / `GetMonitorInfo` 取前台窗口所属显示器完整 `rcMonitor`，仅在窗口非最大化且覆盖完整 monitor bounds 时标记 `isFullScreen: true`；`ScreensaverEligibilityGuard` 基于该 `isFullScreen` 与完整 `display.bounds` 拒绝真正全屏，最大化普通办公窗口返回 `canInterrupt: true`，仅非最大化无边框窗口覆盖完整 `display.bounds` 时才视作演示并拒绝。`stale_cache` / `unknown-state` / `provider-error` / `display-query-failed` 与界面感知禁用语义保持不变。
- **S-02**：渲染器 `ScreensaverSystem` 的 `waiting_for_input` 终态改为显式循环边界；可用 Overlay 不少于两个时按固定顺序 `shareFood → hug → kiss` 过滤后持续循环至用户输入或静默取消，零或一个可用 Overlay 时停在中心 `idle_waiting`。普通输入在 `entering` / 任意 `performing` 阶段进入一次性 `caught → runningBack`，`caught` / `runningBack` 状态忽略重复 `input` stop，确保感叹号与回位各至多发生一次；静默 `screensaver-cancel` 仍立即重置。
- **S-03**：触发等待档位由共享 `screensaverAllowedMinutes.js` 统一为 `1 / 3 / 5 / 10 / 15 / 30` 分钟（默认 5），旧持久化值 `60` 在首次读取时迁移为 `30` 并回写 store；托盘子菜单渲染六个 radio 项并追加一条中英日三语 `trayScreensaverPowerHint` 不可点击提示，说明 Windows 关屏/睡眠时间须晚于所选等待时间，应用不读取或修改电源策略。

## 使用方式

本文件用于汇总 CP 屏保实际试用后发现的问题、期望与取舍。每项意见先记录问题、目标行为和验收标准；所有意见收集完成后，再据此产出有依赖顺序的修改计划。本文件本身不改变已发布行为，也不作为实现授权。

## 待纳入修改计划的策略

> 以下三项均已实施，详见上文《已实施的落实情况》。

### S-01：区分最大化办公窗口与真正的全屏/演示状态

**问题**

当前 Windows `ScreensaverEligibilityGuard` 将“前台窗口覆盖任一显示器的整个 `workArea`”判为 `presentation` 并拒绝 CP 屏保。常规最大化的 VS Code、Office 等办公窗口通常满足这一条件，因此用户离开电脑休息时，屏保会被错误阻止；关闭“界面感知”后才会触发。

该保护的初衷正确：不能在 PPT 放映、视频全屏或其他演示活动上绘制桌宠演出。但“覆盖工作区”只是全屏的粗略代理，无法区分日常最大化办公与真正不应打扰的演示。

**目标策略**

- 最大化的普通办公窗口必须允许 CP 屏保在达到闲置阈值后触发。
- 真正的全屏、无边框演示或明确的演示状态必须继续阻止触发；会话进行中进入这类状态也必须静默取消。
- 活动窗口信息未知、缓存过期、采样/显示器查询失败时继续 fail-closed，不能为了提升触发率而放宽这项安全保护。
- “禁用界面感知”保留为用户的全局开关和诊断手段，不应成为正常使用 CP 屏保的必要步骤；其既有的窗口平台感知影响范围不得被意外改变。

**实现方向（待计划阶段确认）**

活动窗口采样已有 `isMaximized` 字段。守卫应将“最大化”与“覆盖工作区”分开处理，并以显示器完整 `bounds`、窗口样式/全屏信号或其他可靠的 Windows 原生信息识别真正全屏，而不是仅凭 `workArea` 覆盖率推断。若现有 PowerShell 采样信息不足，应先确定可验证的数据源，再调整守卫契约。

**验收标准**

1. 最大化 VS Code、Office 等普通窗口前台且电脑闲置超过阈值时，CP 屏保会触发。
2. 真正全屏/演示场景中，CP 屏保不会触发；已开始的会话会取消且不播放“被抓包”退出动画。
3. `stale_cache`、`unknown-state`、`provider-error`、`display-query-failed` 仍全部拒绝触发。
4. 保持启用界面感知时即可满足第 1 项；关闭它不再是常规办公场景的规避措施。

**已确认事项**

- 首发验收至少覆盖 PPT 放映与浏览器 F11 两种 Windows 全屏演示形态。
- 对无边框但未标记全屏的应用，采用保守规则：非最大化窗口覆盖完整 display bounds 时视为演示并拒绝触发。

### S-02：闲置期间循环 CP 连招，输入后以“被发现”反馈退出

> 进度：普通输入后的 `!` 已调整为保留一次绘制机会、展示 800ms 且按 DPI 对齐；连招循环仍待实施。

**问题**

当前屏保只播放一组“idle → hug 等互动 Overlay → idle”动作；该组结束后，两只宠物停在场景中央等待用户输入。用户持续闲置时，演出没有继续进行，视觉上像屏保很快结束；用户恢复输入时也没有稳定、可见的“被发现”提示，直接回到原位的反馈不足。

**目标策略**

- 在同一段连续闲置中，至少有两个可用互动素材时，第一组动作结束后必须继续播放下一组 CP 连招，持续循环至用户恢复输入或会话被静默取消；仅有零或一个可用互动素材时，安全地停在中心 idle 等输入，不循环单个互动。
- 每组动作之间保留中心 idle 作为自然过渡，但不能将它视为演出终态或自动回位的信号。
- 正常用户输入恢复时，双宠必须先显示一次清晰的“被发现”反馈：至少为头顶感叹号；可选或后续确定为配套的短对话气泡（例如“不好了，被发现了！”），随后再执行逃回入场前坐标的动画。
- 锁屏、睡眠、全屏/演示、隐藏、暂停、禁用或显示器变化等静默取消继续立即恢复坐标，不能播放“被发现”反馈，也不能继续循环。
- 同一 `sessionId` 的重复 stop/cancel 或迟到 IPC 不得重复显示感叹号、对话或回位动画。

**实现方向（待计划阶段确认）**

将 renderer 的屏保状态机从“一次动作序列完成后等待”扩展为显式的循环阶段：`entering → playingCycle → idleBetweenActions → playingCycle`，直到主进程以普通输入发出匹配 session 的 `screensaver-stop`，再进入一次性的 `caught → runBack → inactive`。静默 `screensaver-cancel` 保持独立的无反馈清理路径。动作选择应复用现有已校验的 CP Overlay 素材；仅当可用动作不少于两个时才进入循环，否则停在中心 idle，避免单个互动反复播放。

**验收标准**

1. 可用互动素材不少于两个时，达到闲置阈值后完成第一组互动仍持续进入第二组及后续组；用户不操作时不会自动回到日常位置。
2. 用户在任一 idle 或互动阶段恢复输入后，仅显示一次“被发现”反馈，再回到两个宠物各自的入场前坐标。
3. 静默取消会立即回位，且没有感叹号、对话气泡或额外 CP 动作。
4. 循环至少跨越两组动作的自动化回归测试通过，并覆盖输入发生在 idle、Overlay 播放中及已取消后的迟到事件。
5. 可用互动素材为零或一个时，不播放或循环单个互动，双宠停在中心 idle 等输入。

**已确认事项**

- 可用互动素材不少于两个时，每轮按固定动作顺序 `shareFood → hug → kiss` 过滤后播放；同一互动不会在相邻轮次中连续重复。仅有零或一个可用互动素材时不播放循环互动，停在中心 idle 等输入。
- “被发现”反馈仅使用 CSS 文本 `!`，本轮不新增对话气泡；气泡留作后续独立需求。

### S-03：调整屏保触发等待档位，并提示系统电源时间的影响

**问题**

现有托盘菜单提供 `1 / 5 / 10 / 30 / 60` 分钟。它缺少适合短暂离开的 `3 分钟` 与常见办公休息的 `15 分钟`，却保留了可见性很低的 `60 分钟`。更重要的是，CP 屏保不会阻止 Windows 关屏或睡眠：在许多 Windows 11 默认电源配置中，接电后约 5 分钟就会关屏或进入睡眠，用户可能误以为 CP 屏保没有触发。

**目标策略**

- 将可选触发等待调整为：`1 / 3 / 5 / 10 / 15 / 30` 分钟；删除 `60 分钟`。
- `1 分钟`仅作为快速验证档位；`3 分钟`覆盖默认 5 分钟关屏/睡眠前的短暂可见演出；`5–15 分钟`覆盖日常办公休息；`30 分钟`保留给低频偏好。
- 在屏保等待菜单或启用后的恰当位置说明：要看见演出，Windows 的关屏与睡眠时间应晚于所选 CP 等待时间；应用不应擅自更改用户的系统电源策略或阻止睡眠。
- 保持对现有持久化值 `60` 的兼容：旧设置不能因升级失效；其迁移/展示方式在实施计划中明确决定。

**验收标准**

1. 托盘只展示 `1 / 3 / 5 / 10 / 15 / 30` 六个合法档位，三种语言文案一致。
2. 选择任一新档位后，重启应用仍保留选择；`3` 与 `15` 分钟能正常触发。
3. 已保存的 `60` 分钟设置有明确、可测试的兼容行为，且不会使功能被静默关闭。
4. 用户可从界面获得“系统关屏/睡眠可能早于 CP 屏保”的简明提示；不修改 Windows 电源设置。

**已确认事项**

- 旧的 `60` 分钟持久化值在首次读取时自动迁移为 `30` 分钟并回写 store。
- 提示采用等待子菜单中的不可点击项，以三语简短说明 Windows 关屏/睡眠时间须晚于所选等待时间；不产生打扰性通知。
